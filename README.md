### 真实数据：上海普陀区曹杨新村街道（1.6 km × 1.6 km）

数据源：百度地图开放平台地点检索（POI，已由 BD-09 换算为 WGS-84）+ OpenStreetMap（步行路网、建筑轮廓）；
**人口按七普街道密度做总量校准**（详见下方"户数口径"）。

| 指标 | 结果 |
| --- | --- |
| 综合体检得分 | **82.8（良好）** |
| 规模 | 98 个居住组团 / 45,209 户 / **117,543 人** / 109 处设施（分析范围内）/ 7,417 路网节点 |
| 15 分钟生活圈范围 | 2.53 km² |
| 最严重问题 | 社区文化活动中心覆盖 **49.4%**、社区卫生服务站 **77.1%** |
| 处方（文化活动中心 +2 处） | 覆盖率 **49.4% → 99.5%** |
| **自算路网 vs 百度步行路径规划** | 距离比中位数 **1.033**、时间比中位数 0.909、**15 分钟判定一致率 96.7%**（30 组抽样） |
| **典型住户的一天**（同一栋楼，5 类人群） | 老人 6 站 / 09:00–13:27；上班族 2 站 / 07:20–07:48；行动不便者 15 分钟只能走 540 m |
| **15 分钟圈可达面积比**（某组团实测） | 实际 1.14 km² ÷ 同半径理想圆 1.89 km² = **60%**，被河道/快速路吃掉 0.76 km² |

> 得分比早期版本（72.8）高，是因为修掉了四个数据口径 bug：① OSM `oneway` 约束的是**机动车**，
> 早期当成行人单行，造出 278 条人工断头路；② 百度 POI 里 "XX酒店(…地铁站店)"、"申亚时代广场"
> 这类商家名会被关键词匹配成地铁站/公园，现在要求 tag/type 二次确认；③ **地图上"没接上的
> 断头路"**（小区内部路画到离大马路几十米处就停了）会把整片组团误判成"什么都没有"；
> ④ **路网抓取范围只有分析方框**，而 15 分钟步行（1125 m）比方框半边长（800 m）还长，
> 贴边组团的圈被硬切一刀 —— 现在外扩 1200 m（分析范围不变）。
> 四条都写在 docs/metrics.md §2.6–2.8，每条都给了前后对比。
>
> 后来又补了第五条：⑤ **百度地点检索是圆形、半径比方形分析范围大一圈**（半边长 800 m → 半径
> 1040 m），框外的住宅区 POI 被当成分析单元，于是"地图上有小区、栅格里却没有色块"，
> 覆盖率也被系统性拉低。现在 OSM 与百度补充走**同一道分析范围判定**，地图上也把分析范围
> 画成虚线框、图例写明"框外不参与体检"（见 docs/metrics.md §2.9）。

第二个真实社区 **长风新村街道**（1.8 km × 1.8 km，七普 120,920 人 / 5.8 km²）也跑通了：
152 个居住组团 / 25,982 户 / 67,553 人 / 113 处设施，综合 **73.9（良好）**——
文化设施与社区食堂缺口更明显，可直接用来做**跨社区对比**。

另外三个自选社区（**北新泾街道** 81.4、**大场镇** 70.1、**程家桥街道** 64.7）
用于验证"换个街道能不能直接跑通"；其中大场镇是"断头路误判"的发现地，
程家桥是"框外居住区被当成分析单元"的发现地。

### 户数口径（三级可信度，自动择优）

| 级别 | 来源 | 怎么用 |
| --- | --- | --- |
| ① 实测 | 街道/居委实测户数 | 放 `data/households/<社区id>.csv`（`name,households[,lon,lat]`），**自动优先并跳过校准** |
| ② 普查总量校准 | 七普常住人口 ÷ 街道面积 → 人口密度 × 分析范围 | 社区配置 `population_calibration`（本项目两个真实社区都已配置） |
| ③ 空间结构 | OSM 建筑轮廓 × 层数 ÷ 91 m² | 默认；**校准只改总量，不改空间分布** |

曹杨新村：七普 98,267 人 ÷ 2.14 km² = 45,919 人/km² × 分析范围 2.56 km² = 目标 117,553 人；
OSM 原始估算只有 39,949 人（偏低 2.94 倍）→ 校准后 117,543 人，综合得分 86.1 → 82.8
（人口被低估时，"供需均衡度"会误判为设施充足）。

### 自选社区（任意地址 → 直接出体检结论）

三种用法，同一套装配逻辑：

```powershell
# 1) 命令行
python tools\add_community.py --name "长风新村街道" `
  --address "上海市普陀区中山北路3671弄长风新村街道办事处" `
  --half-width 900 --population 120920 --area 5.8
python tools\build_demo.py custom-078ed4        # 出报告

# 2) 网页：右上角「＋ 自选社区」→ 填名称/地址/范围（可选常住人口与面积）→ 开始分析（20–60 秒）
#    也可用 http://127.0.0.1:8000/?new=1 直接展开面板

# 3) API
POST /api/communities   {name, address|lon/lat, half_width, population?, area_km2?}
DELETE /api/communities/{id}
```

流程：地址 → 百度地理编码（BD-09 → WGS-84，返回置信度并在偏低时警告）→
百度地点检索拿 POI + Overpass 拿步行路网与建筑 → 户数校准 → 自动加入社区列表并渲染。
原始响应全部缓存，重复运行不再耗时耗配额。**需要外网**；无外网时用内置合成社区仍可完整演示。

> 曹杨新村是上海最早的生活圈试点之一，体检结论（"总体良好，缺的是社区文化设施与基层医疗"）
> 与直觉一致。误差分析那两行是本项目最"硬"的证据：自建路网与官方步行路径的距离几乎一致
> （差 3%），时间差几乎全部来自假设步行速度（本项目 1.25 m/s vs 百度隐含 1.13 m/s），
> **15 分钟阈值判定一致率 96.7%**——也就是说"某组团是否达标"这个结论基本不会被推翻。
> 少数离群样本（时间比 >2）来自 OSM 与百度路网拓扑差异（缺人行桥/门禁/围墙），已在报告中标出。

## 3. 技术要点（也是答辩要点）

1. **可达性自算，不依赖厂商批量算路配额**。OSM/合成路网 + Dijkstra（标准库 heapq 手写），
   设施与组团吸附到最近路网节点并把"离路距离 ÷ 步行速度"作为惩罚时间计入。
   配额被卡、接口变更都不会让项目停摆，而且算法可解释、可复核。
2. **生活圈范围 = 所有居住组团 15 分钟可达区域的并集**，不是社区中心的一个圆。
3. **体检图以"可达必需要素数量"着色**（而不是最短时间）——时间并集几乎处处都是绿色，
   要素数量才能把服务洼地直接画出来。
4. **双向口径**：既测"该有的有没有"（覆盖率、达标率），也测"是否只靠一处"（单一依赖率）
   与"组团之间是否公平"（加权 Gini），还测"5 分钟便利度梯度"。
5. **处方可落地**：选址优化只对 `sitable=true` 的要素开处方（不会建议"新建一座地铁站"），
   用贪心最大覆盖 + 1-opt 局部搜索，输出推荐点位、新增覆盖户数与前后对比。
6. **数据源可插拔**：`synthetic` / `osm` / `baidu` 三种 provider 产出同一份 `Dataset`，
   引擎、指标、报告、前端零改动。
7. **规划助手是"因人而异 + 因时而异"的**：同一个组团，换一类住户（`config/personas.json`）
   就换一条出行链、一个步速、一套开放时段约束。**画像不接大模型现场判人** ——
   规则表可核对、可复现、离线可用；大模型只适合出现在两头（解析自然语言、把结论翻成人话），
   绝不进入中间（否则不可复现、离线失效、演示有延迟风险）。
8. **15 分钟圈画成真实路网上的等时圈，不画几何同心圆**：台风圈是理想圆，隔着一条河、
   一条快速路，真实的圈形状完全不同 —— 画成圆等于放弃"用了真实路网"这个最大的技术差异点。
   借的是风圈的视觉语言（分层色带 + 等时线 + 圈上刻度 + **可达面积比** + 被切断的方向）。
9. **步速乘进生活圈**：同一条路，成人 15 分钟走 1125 m、老人 765 m、助行器 540 m。
   所以"达标"必须和"谁在走"一起说 —— 报告里同一个组团可以同时出现
   "成人口径达标"与"助行器口径一项都走不到"，这不是矛盾，是结论。

9. **动词与数字都要经得起追问**：tier1/tier4 写「邻近」、tier2/tier3 写「可合署」，
   不用含糊的"依托"；每个数字都带上口径（"15 分钟可达覆盖率 49.4%"，
   而不是"49.4% 人口可在 15 分钟内到达"）。对外文案统一口径见 docs/metrics.md §16。

## 8.1 真实数据的已知局限（必须主动写进答辩）

1. **坐标系统**：百度（BD-09）与 OSM（WGS-84）在上海相差约 **1.16 km**，本项目已统一换算为
   WGS-84（`lifecycle_metrics/crs.py`，实测精度 < 10 m，回归测试钉住）。**这是最容易踩的坑**——
   不换算的话 POI 与路网整体错位，所有可达性结论都是错的。
2. **底图分辨率**：百度 zoom 的分辨率**不是** Web Mercator —— 实测为
   `262150·cos(lat)/2^zoom`，与标准公式（156543.03）差 **1.675 倍**。用错会让静态底图整体缩放，
   表现为"中心对得上、越往边缘越偏"。已用 JSAPI `getBounds` + `pointToPixel` 双口径在
   zoom 14–18 标定（`tools/basemap_scale_check.py`），核验图 `align_check.png` 全图对齐。
2. **人口是估算值**：OSM 建筑轮廓 × 层数 ÷ 91 m²，本片区算得 4.1 万人，街道实际约 10 万量级，
   偏低较多（OSM 建筑覆盖率不足）→ 报告中的"覆盖人口"应视为下限；覆盖率、可达时间等
   比值类指标受影响很小。有实测户数时应替换。
3. **POI 是多源并集**：百度地点检索为主，OSM 补充小微设施（记录在 `meta.poi_by_source`）。
   未归类样本打印在 `meta.unclassified_samples`，便于继续调映射表。
4. **地铁/公交站做了空间合并**（250 m / 60 m），否则同一站的多个出入口会被算成多个站点。
5. **百度接口有并发配额**：步行路径规划触发时返回 `status=401 当前并发量已经超过约定并发配额`，
   已加 0.45 s 限速与退避重试；地点检索结果全部落盘缓存，重复运行不消耗配额。
6. **浏览器端 JSAPI 可能被本地环境拦截**：已内置服务端静态底图兜底
   （`/api/basemap.png`，走服务端 AK），JSAPI 失败时前端自动切回 canvas 模式并继续显示真实地图。
7. **Overpass 镜像不稳定**：实测 `overpass-api.de` 与 `overpass.osm.ch` 可用，
   其余镜像常年超时；可用 `OVERPASS_URL` 环境变量指定，原始响应缓存到 `data/cache/`。

## 8.3 选址模型（可建性约束）

早期版本只优化可达性，会把设施推荐到河道、机关院内、校园里。现行模型：
**候选点必须落在载体梯队周边（1–4 梯队）+ 排除不宜区 + 同类间距达标**，再按
新增覆盖户数 × 梯队系数 排序。完整口径、数据来源与局限见 docs/siting.md。

实测曹杨新村街道：载体 101 处（地铁出入口 11 / 社区服务设施 28 / 商业 45 / 公共设施 17），
第五梯队（公交枢纽/地下通道/闲置亭棚）因百度 POI 取不到已放弃（实测 0 处），梯队编号保留 1–4；
禁建区 40 处，水体与河道 15 处；候选点 1108 个，**筛除水体内 80 个、禁建区内 141 个、同类过近 80 个**；
推荐 P1 = 中宁路地铁站-3 口 126 m（第一梯队 ×1.5，新增覆盖 18,688 户），

## 8.4 交互上的四个便利功能

1. **模糊搜索街道**：/api/geocode/search 走百度地点检索（不是地理编码），
   所以曹杨新村街道长风新村打浦桥街道这类不完整输入都能出候选列表，
   每条带名称、地址、行政区与 WGS-84 坐标，点选即作为分析中心 —— 不再要求用户输入精确门牌地址。
2. **优化后覆盖图**：点「运行选址优化」后，系统把推荐点位作为新设施代入模型**重算一遍完整体检**，
   顶部出现「现状 / 优化后」切换，覆盖色带与组团达标配色一起切换，面板给出
   **综合得分与六维指标的 before → after**，报告里也生成 map_after.png。
   曹杨新村实例：综合得分 **78.0 → 81.0**，可达覆盖率 84.6 → 89.1。
3. **点位画像（新增设施描述）**：每个推荐点位自动生成"建什么形态、多大规模、谁受益、跟谁合署"——
   受益组团数与服务人口、到该点步行时间的中位/最长值、可合署的既有设施、
   容量核对（按工程假设值）、审批要点与载体约束。数据全部由已有结果算出，
   建设形态/规模/审批来自 `config/elements.json` 的 `build_notes`（**工程建议，非标准强制条款**）。
4. **一天动线（点居住组团）**：在地图上点任一个房子图标，就沿步行路网排出"这个组团把必需要素
   各走一遍"的动线：逐段的到访时刻、步行分钟与米数、每处停留时长（可改）、
   回家段、以及**这一趟走不到的要素（缺口）**；支持「现状 / 优化后」两个场景与
   「生活动线序 / 就近串点序」两种排法对比（后者回答"只图省腿脚能省多少分钟"）。
   曹杨新村实例：颐宁苑出发，现状 9 处停靠、步行 85.5 分钟、2 项走不到（卫生站 18.7 分钟、
   文化活动中心 26.1 分钟）；把 P1/P2 代入后缺口降为 1 项。
   口径与假设见 docs/metrics.md §6 —— **15 分钟生活圈 ≠ 一天只走 15 分钟**。

> 注：新增设施后「冗余度（抗风险）」可能略降——刚被覆盖的组团往往只依赖这一处新设施，
> 属正常过渡效应，继续增补第二处即可回升。

## 8.5 答辩加固三件套（都是本地计算，不联网、不耗地图额度）

1. **标准依据表**：每个要素挂 `config/elements.json::standard_ref`（配置层级 / 标准名称 /
   应配置·宜配置 / 步行距离口径 / 建筑面积 / source_url / `verified`）。
   本项目的 15 分钟 = 1000 m、5 分钟 = 300 m 与 GB 50180-2018 表 3.0.4 的步行距离分级一致；
   出处来自公开检索，**12 条全部标「待核对原文」**，核对完把 `verified` 改成 `true` 报告即自动更新。
2. **结论稳健性**：把步速（1.10/1.25/1.35 m/s）与阈值（810/900/990 s）各动一动重算 7 个情景。
   曹杨新村得分区间 **79.3–85.3**（跨度 6.0），但**最短板要素在所有情景下都是社区文化活动中心**——
   所以引用时应给区间，而"该补什么"的方向是稳的。`python tools/robustness.py`
3. **边际效益曲线**：k=1/2/3/4 各跑一遍，回答"为什么是 2 处"：
   曹杨第 1 处 +19,033 户 → 第 2 处 +3,620 → 第 3 处 +221 → 第 4 处 **+0**。
   累计口径用**并集**（基线不可达人口 − 建后不可达人口），不能把各点位自报新增相加
   （会多算 68%）。`python tools/marginal.py`
