## 0. 空间与时间口径

| 项 | 取值 | 说明 |
| --- | --- | --- |
| 15 分钟生活圈 | 步行 900 s / 约 1000 m | 对应 GB 50180-2018 十五分钟生活圈居住区（步行距离 800~1000 m） |
| 5 分钟近距 | 步行 300 s / 约 300 m | 对应五分钟生活圈居住区（步行距离 300 m） |
| 步行速度 | 按道路类型 1.10–1.32 m/s | `providers/synthetic.py` 与 `providers/osm.py` 中的 `SPEED` / `HIGHWAY_SPEED` |
| 可达性算法 | 路网最短路（Dijkstra）+ 吸附惩罚 | 见下文 §2 |
| 家庭规模 | 2.6 人/户 | 可配置；有实测人口时应替换 |

## 1. 六项指标

| 维度 | 定义 | 计算式 | 权重 |
| --- | --- | --- | --- |
| **15 分钟可达覆盖率** `coverage` | 必需要素中，居住人口可在 15 分钟内到达该要素的比例 | 每个要素先算户数加权覆盖率，再对必需要素等权平均 | 0.28 |
| **要素达标率** `compliance` | 11 项必需要素**全部**可达的居住人口占比 | 组团达标得分 = 1 − 缺失要素数 / 必需要素数；按户数加权平均 | 0.26 |
| **供需均衡度** `supply_demand` | 设施相对服务能力与覆盖人口的匹配程度 | `gap_index = max(0, 1 − 供给人口/需求人口)`；维度得分 = 1 − 各要素 gap 均值 | 0.18 |
| **冗余度（抗风险）** `redundancy` | 同一要素有 ≥2 处可达的人口占比 | 维度得分 = 1 − 各要素单一依赖率均值；单一依赖率 = 仅 1 处可达的户数 / 已覆盖户数 | 0.10 |
| **公平性** `fairness` | 组团之间达标得分的均衡程度 | 维度得分 = 1 − 加权 Gini（权重=户数） | 0.10 |
| **5 分钟近距便利度** `proximity_5min` | 5 分钟步行可达要素的人口占比 | 对必需要素等权平均 | 0.08 |

**综合得分** = Σ(维度得分 × 权重) × 100；等级：≥85 优良 / ≥70 良好 / ≥55 一般 / <55 短板明显。

> 口径说明：原计划中的「绿色可达性」在本版被替换为「5 分钟近距便利度」——
> 因为本版只建模步行一种方式，"绿色出行占比"恒为 100% 没有区分度，
> 而"便利度梯度"（5 分钟 vs 15 分钟）能真实反映生活圈质量。若要恢复绿色可达性，
> 需引入骑行路网与速度模型。

## 2.5 户数口径（三级可信度，报告里必须写清）

户数是所有"人口加权"指标的基础，本项目按可信度从高到低处理，**高优先级自动覆盖低优先级**：

| 级别 | 来源 | 触发方式 | 记录位置 |
| --- | --- | --- | --- |
| ① 实测 | 居委/街道实测户数（拿到就能用） | 放 `data/households/<社区id>.csv`（`name,households[,lon,lat]`） | `meta.household_overrides` |
| ② 普查总量校准 | 七普常住人口 ÷ 街道面积 = 人口密度 → × 分析范围面积 = 目标人口 | 社区配置里的 `population_calibration` | `meta.population_calibration` |
| ③ 空间结构 | OSM 建筑轮廓 × 层数 ÷ 91 m²（= 35 m²/人 ÷ 2.6 人/户）；OSM 建筑覆盖不足时用百度「住宅区/小区」POI 补空白 | 默认 | `meta.residential_source` |

**③ 的补空白规则**：OSM 建筑在部分区域很稀（实测自选社区出现过 1.6 km 见方的街道只认出
23 个组团、2,324 户，而图上明明有十几个成片小区），此时地图上会出现"色块铺开、居民区图标
却缺席"的错位观感。触发条件 = OSM 推算的户数密度 < **3000 户/km²**
（`RESIDENTIAL_DENSITY_FLOOR`；上海中心城区实际约 1–1.5 万户/km²）：
用百度地点检索「住宅区 / 小区」补点，**只在距已有 OSM 组团 > 150 m 的空白处补**
（`RESIDENTIAL_DEDUP_M`），户数取**邻近 OSM 组团的中位数**，保证与 OSM 组团同量纲，
不会凭空放大总户数。补点记为 `residential_source = osm+baidu`、`residential_baidu_added`。

**关键设计**：②③ 只调整总量，**空间分布仍沿用 ③ 的结构**——所以它改变的是"绝对人口规模"，
而不是"哪里缺设施"。实测 CSV 存在时自动跳过总量校准（实测优先，避免把真实数据又缩放回去）。

**幂等性**：数据集带缓存复用，重复装配必须还原到原始户数再缩放，否则会复利缩放
（踩过的坑：77,745 → 再乘 0.87 → 67,543）。实现见 `pipeline.py::_restore_base_households`，
回归测试 `TestPipeline::test_calibration_is_idempotent`。

**曹杨新村街道实例**：七普常住人口 98,267 人（citypopulation.de）÷ 街道面积 2.14 km²
（tcmap.com.cn）= 45,919 人/km² × 分析范围 2.56 km² = 目标 117,553 人；
OSM 估算原本只有 40,989 人（偏低 2.87 倍），校准后 117,556 人。
校准前综合得分 81.8 → 校准后 78.0：因为「供需均衡度」要按真实人口算，
人口被低估时设施看起来是够的。

## 2.6 路网与 POI 的两个口径修正（都会实打实改变分数）

**① 行人单行只认 `oneway:foot`。** OSM 的 `oneway=yes` 约束的是**机动车**（单行道两侧的
人行道照样双向通行）。早期直接读 `oneway` 建图，曹杨路网 2107 条边里有 **278 条被误判为行人单行**，
造出"能走进公园、走不出来"的人工断头路：`shortest_path(健身点 → 公园)` 直接返回 None，
"一天动线"走到一半断掉。改为 `tags.get("oneway:foot")` 后，曹杨综合得分 72.8 → **79.3**
（后续又因 POI 分类修正微调到 78.0）——可见"路不通"对可达性的影响是量级级别的。

**② 百度 POI 必须用 tag/type 二次确认，不能只看名称。** 名称里带关键词的商家太多，
实测曹杨 9 个"地铁站"里 5 个是 `XX酒店(…地铁站店)`、停车场、`…通道口-长城大厦` 这类 POI；
`申亚时代广场`（写字楼）、`星星充电充电站(申亚时代广场直流)` 被算成公园；
`曹杨社区卫生服务中心-地上停车场` 被算成一处卫生站。现在：

| 规则 | 内容 |
| --- | --- |
| `kind_ok()` | metro 要求 tag/type 含 `地铁站/轻轨站/轨道交通站`；bus_stop 要求含 `公交/巴士/车站/枢纽`；park 要求含 `公园/绿地/风景/景区/游园/植物园/园林/花园/广场` |
| `is_auxiliary()` | 停车场、充电站、出入口、`…口` 结尾的地铁出入口一律不作为独立设施 |
| 组团实名 | 只有"居住组团 N"这种通用名的组团，挂上 250 m 内最近百度「住宅区/小区」POI 的名字（`tools/name_clusters.py`），报告与动线里才能直接说"金菊小区""曹杨八村" |

修正后曹杨地铁站从 9 处降到 **4 处**（枫桥路、中宁路、曹杨路、真如，与实际情况一致），
综合得分 79.3 → 78.0。回归测试：`TestPoiClassification`。

## 2.7 路网连通性：断头路补连 + "无法评估"如实标注

**现象**：自选社区「大场镇」里，阳城贵都社区（69 户）周边明明全是店，却显示"达标得分 0、
11 项必需要素全部不可达"。查下来不是它没有设施，而是 **OSM 里这条小区内部路画到离永和路
55 m 的地方就停了**（画图的人没 snap），而我们的建图只按"端点坐标重合"合并 —— 于是这段
内部路成了孤岛；掉进孤岛里的组团，Dijkstra 在岛内找不到任何设施，就被算成 0 分。

**为什么以前没暴露**：孤岛本身很常见（曹杨 6 块、大场镇 7 块），只有当"某个居住组团恰好
吸附到孤岛"时才发作；而且它**伪装成规划结论**——进问题清单、拉低覆盖率与公平性。

| 社区 | 修复前（孤立组团按 0 分） | 修复后 | 被误判的组团 / 户数 | 孤岛到主路网 |
| --- | --- | --- | --- | --- |
| 曹杨新村 | 78.0 | **78.1** | 1 个 / 396 户 | 16.7 m |
| 长风新村 | 70.8 | **71.0** | 0 | — |
| 北新泾 | 75.4 | 75.4 | 0 | — |
| 程家桥 | 59.0 | **60.3** | 3 个 / 185 户 | 22.6 m（隔水，走别的缺口接上） |
| 大场镇 | 59.8 | **66.3** | 5 个 / 387 户 | 45.5 / 34.5 m |
| 合成数据集 | 69.9 | 69.9 | 0 | — |

**做法一：把断头路接起来**（`network.stitch_components`，参数都在实测数据上定过）

1. 把所有**跨连通块**且相距 ≤ **60 m** 的路网节点对按距离从近到远排序，依次连接
   （最小生成森林思路）—— 保证补出来的每一处都是"最近的那个缺口"，不多连、不绕远；
2. **跨水不连**：连线落在水面多边形内或贴河道中线 ≤ 6 m 就跳过（程家桥有一例隔水，
   硬连等于凭空造一座桥）；
3. 每处补连写进 `meta.stitched_edges`（两端坐标、长度、连通块编号），报告里可逐条复核。
   实测 6 个社区共补 2–7 处，长度 10–51 m。同时接进 provider（`providers/osm.py`），
   以后重建数据自动生效；存量数据用 `tools/stitch_network.py` 就地补（纯本地，不联网）。

**做法二：接不上的就明说"无法评估"**（`network.analyze_network` + `metrics.diagnose`）

- 组团吸附到的连通块里**一处设施都没有** → 标记 `network_status = isolated`；
- 这类组团**不计入覆盖率/达标率/公平性的分母，也不进问题清单**，改单列
  `diag.data_quality`（含组团名、户数、块大小），界面用**灰色房子**表示、动线直接说
  "无法评估（不是没有设施）"；
- `summary` 里同时给出 `assessable_*` 与 `unassessable_*` 两组人口，报告第 6 节列出
  「数据质量与路网连通性」。补连后各社区 `unassessable_households` 均为 0，
  但这套兜底必须留着：真实数据里总会有连不上的地方（隔水、门禁、OSM 缺失）。

回归测试：`TestNetworkStitching`（补连生效 / 跨水不连 / 孤立组团被标注且不污染指标）。

## 2.8 抓取范围外扩 1200 m（分析范围不变）

**问题**：15 分钟步行 ≈ 1125 m，比分析方框的半边长（800–900 m）还长。OSM 抓取范围如果
就等于分析方框，贴边组团的 15 分钟圈会被"盒子边缘"硬切一刀 —— 它明明走得出去，
但框外没有路可走。这会让**所有贴边组团的可达性系统性偏低**。

**做法**：`providers/osm.py::build_osm_dataset(fetch_margin_m=1200)` ——
抓取 bbox 在分析 bbox 基础上外扩 1200 m（≈ 一次 15 分钟步行），而：

| 保持不变 | 说明 |
| --- | --- |
| `community.extent_m` | 栅格范围、地图视野、前端画布、选址候选区都按它 |
| 居住组团 | 只取**分析范围内**的建筑做聚合（否则户数/人口口径会随抓取范围漂移） |
| 设施"点位数"统计 | `summary.facilities` 只数分析范围内的；`facilities_fetched` 才是抓到的总数 |
| 可达性计算 | **用全部设施**——框外那家菜场居民照样走得到，这正是修这个问题的目的 |

**效果**（同一套数据、同一套口径，只改抓取范围）：

| 社区 | 外扩前 | 外扩后 | 路网节点 | 框内设施 |
| --- | --- | --- | --- | --- |
| 曹杨新村 | 78.1 | **82.8** | 1,890 → 7,417 | 109 |
| 长风新村 | 71.0 | **73.9** | 2,488 → 10,192 | 113 |
| 北新泾 | 75.4 | **80.8** | 1,434 → 5,332 | 85 |
| 程家桥 | 60.3 | **64.7** | 1,050 → 4,470 | 35 |
| 大场镇 | 66.3 | **69.9** | 793 → 4,554 | 55 |

提升 2.9–5.4 分，说明"边界硬切"是系统性低估，不是个别现象。

**顺带修的一个坑**：Overpass 镜像超时后会返回 `{"elements": []}`，早期代码把它当正常响应
落盘缓存，之后每次重建都得到一张空路网（表现为 `AssertionError: self._index is not None`，
极难排查）。现在空结果与含 `remark` 的响应都视为失败 → 换镜像重试，且**不落盘**。

## 2.9 分析范围的边界必须画出来（框外居住区不是分析单元）

**问题**：百度地点检索是**圆形**检索，半径 = `max(半宽, 半高) × 1.3`（半边长 800 m →
半径 1040 m，四角更远），比方形**分析范围**大一圈。OSM 侧的居住组团一直有
"只取分析范围内"的判定（`providers/osm.py: in_core`），**百度住宅区补充路径漏了这道判定**。

后果是三个口径同时被污染：

| 后果 | 说明 |
| --- | --- |
| 图与数据对不上 | 栅格只覆盖分析范围，框外组团没有对应格子 → 地图上有小区、却没有色块 |
| 系统性拉低覆盖率 | 设施只统计分析范围内的，框外组团只能在更远的条件下评估 |
| 社区之间不可比 | 框外部分取决于"检索半径 ÷ 分析框面积比"，各社区并不相同 |

**做法**：`providers/baidu.py::in_analysis_box()` —— 与 OSM 完全同一口径，只裁
**"新增组团"**这一步；`baidu_resid` 完整列表仍然用于 `name_clusters_from_poi`
（贴边的框内组团常由框外 250 m 内的小区取名，裁掉会让它们退回"居住组团 37"）。
`meta.residential_poi_outside_box` 记录本次框外 POI 个数，`meta.residential_scope_note` 写明口径。

**效果**（同一套数据、只加这道判定，重建走本地缓存、不耗额度）：

| 社区 | 分析范围 | 检索半径 | 组团 | 户数 | 框外组团 | 得分 |
| --- | --- | --- | --- | --- | --- | --- |
| 曹杨新村 | 1.60 km | 1040 m | 98 → 98 | 45,209 → 45,209 | 0 | 82.8 → 82.8 |
| 长风新村 | 1.80 km | 1170 m | 152 → 152 | 25,982 → 25,982 | 0 | — |
| 北新泾 | 1.60 km | 1040 m | 65 → **55** | 6,996 → **5,966** | 10（1,030 户） | 80.8 → 81.4 |
| 程家桥 | 1.60 km | 1040 m | 62 → **56** | 3,890 → **3,510** | 6（380 户） | 64.7 → 64.7 |
| 大场镇 | 1.60 km | 1040 m | 82 → **77** | 9,766 → **9,433** | 5（333 户） | 69.9 → 70.1 |

框外组团 100% 是百度补充点（OSM 侧框外数为 0）；框外 POI 仍有 13 / 8 / 9 个用于命名。

**同时修复的两件相关事**：

1. **分析范围框上线**。抓取范围比分析范围大 1200 m，底图上框外必然还有住宅区与设施标注。
   现在在体检底图、等时圈图、GL 覆盖图层（canvas 与 JSAPI GL 双模式）上统一画出**虚线分析范围框**，
   图例与图注写明"框外不参与体检"。此前这条口径只写在文档里，界面上从未露面 ——
   这正是"地图上有小区、却没有色块"被读成 bug 的直接原因。
2. **"被切断的方向"不再误报**。`isochrone.py` 的 16 方向射线此前不区分"撞到分析范围边界"
   与"被路网切断"：贴着边缘的组团会被写成"南侧被切断 190 m"，其实只是走到了范围边上。
   现在每个方向带 `limited_by: network | extent`，`extent` 的不计入 `blind_directions`，
   并以 `extent_limited_directions` 单独列出。顺带修掉射线格子索引的 `int()` 向零截断
   （负坐标会被算成第 0 格，射线最多多走一整格才判越界），改用 `math.floor`。

**已知局限**：跨界的居住区按质心整体保留或整体剔除（与 OSM 侧一致）；框外居住区不产生
分析单元，因此"框外小区没有色块"在视觉上仍然存在 —— 但这次是**口径边界**，不是数据矛盾。

## 3. 三个必须说清的技术口径（评委会问）

> 编号从 1 开始（上节为 2.5，本节顺延为 3）。

1. **可达性自算，不依赖厂商批量算路**。用路网最短路计算；设施与居住组团都吸附到最近
   路网节点，并把"离路距离 ÷ 步行速度"作为惩罚时间计入（否则会把藏在小区深处的设施
   算成"门口就有"）。优点是配额被卡项目也不停摆，且算法可解释、可复核。
   **已用百度步行路径规划抽样标定**（`tools/calibrate_walk.py`，曹杨新村 29 组）：
   距离比中位数 **0.983**（自算路网与官方路径几何几乎一致），时间比中位数 **0.906**，
   **15 分钟判定一致率 89.7%**；时间差几乎全部来自速度假设差异
   （本项目 1.25 m/s vs 百度隐含 **1.08 m/s**）。
   → 若要更贴近官方口径，把 `walk_speed_mps` 调到 1.1 左右重跑；对处于 800–1000 s
   临界区间的组团应单独复核（这一区间正是一致率损失的来源）。
2. **生活圈范围 = 所有居住组团 15 分钟可达区域的并集**，不是以社区中心为圆心的缓冲区。
   体检图底图用"该位置 15 分钟内可达的必需要素数量"着色，而不是最短时间——
   时间并集几乎处处都是绿色（因为总有一个组团很近），要素数量才能暴露服务洼地。
   **着色范围有居住用地蒙版**：可达要素栅格是按路网铺开的，直接整片铺色会盖到河道、
   校园、商场、待建地上，看图的人会问"这块颜色跟居民区对不上"。所以色块只铺在
   **① 居住组团周边 150 m 以内 且 ② 非水体**（OSM 水面多边形 + 河道线两侧 12 m）的格子上。
   蒙版只影响显示，**不参与任何指标计算**（覆盖率、达标率、可达时间都不用蒙版），
   统计口径见 `meta.grid_counts.mask`（`resid_buffer_m / masked_total / masked_water`）。
   实现：`accessibility.build_livable_mask()`。
3. **供需缺口是相对模型**：`service_pop_per_unit`（每处设施对应服务人口）是**工程假设值**——
   国标与导则规定的是"应配置某设施"，并未规定每处服务人口。该参数只影响「供需均衡度」这一个维度，
   不影响覆盖率、达标率、可达时间等硬指标；有实测服务能力（面积/床位/班数）时应替换该参数。

## 5. 一天动线的口径与假设（交互式演示，不进报告正文）

点地图上任一居住组团 → `/api/route` → 沿步行路网排出"把这个组团的必需要素各走一遍"的动线。
它是**同一套可达性结果的另一种表达**（不新增任何计算口径），但有几个必须说清的点：

1. **15 分钟生活圈 ≠ 一天只走 15 分钟**。它指"从家出发 15 分钟能到达的设施集合"，
   所以动线里逐段比较"本段步行是否在 15 分钟内"，而不是全程总时长。
2. **出发点是居住组团质心**（组团是 120 m 网格聚合出的分析单元），不是某一栋楼。
3. **停留时长、出发时刻、到访顺序都是情景假设**，界面上可调（`DEFAULT_STAY_MIN` 给默认值：
   买菜 15、食堂 40、接送 10/8、卫生站 20、药店 8、活动中心 45、健身 40、公园 40，
   公交与地铁只作"顺路经过"不计停留）。**不是实测作息**，有街道调研数据应替换。
4. **两种排法在同一批候选里挑，保证可比**：`order=day` 按生活动线序
   （买菜→接送→就医→午饭→活动→散步），但每一步在当前位置附近挑该要素最近的一处；
   `order=nearest` 纯就近串点。两者的步行分钟差就是"日常顺序的代价"（曹杨颐宁苑约 11.6 分钟）。
5. **离路段单独画虚线**：住户与设施都要吸附到最近路网节点，实测有 5–60 m 离路距离；
   折线只走路网，最后一小截用虚线表示，避免看起来"穿墙"。
6. **走不到的要素显式中断并给出最近距离**（用 2 倍阈值再搜一次，例如"最近一处 18.7 分钟"）——
   这是短板可视化最直观的形态：不是"绕一会儿"，而是这一趟根本去不了。
7. 每处设施的离路距离算**两次**（进去一次、出来一次），否则总时长会少算几分钟；
   `alternatives.chosen_min` 与逐段之和必须相等（回归测试 `TestDayRoute`）。

## 8. 标准依据、稳健性、边际效益（答辩加固三件套）

### 8.1 标准依据表（`config/elements.json::standard_ref`）

每个要素都挂了字段：`level`（配置层级）/ `doc`（标准或文件名称）/ `requirement`（应配置·宜配置）/
`walk_distance_m`（该层级的步行距离）/ `building_area`（标准有规定时）/ `source_url` / `verified`。

- **我们的阈值与国标同源**：本项目 15 分钟 = 1000 m、5 分钟 = 300 m，与 GB 50180-2018
  表 3.0.4 的步行距离分级（五分钟 300 m / 十分钟 500 m / 十五分钟 800–1000 m）一致；
- **诚实标注**：出处来自**公开检索**（每条带 source_url），不是逐字核对原文得到的，
  所以 12 条全部是 `verified: false`，报告里显示「待核对原文」。
  核对完把该字段改成 `true`，报告自动去掉标记 —— 这是一个留给人工的开关，不是装饰。

工具：`python tools/add_standard_refs.py`（幂等，只补字段）。

### 8.2 稳健性检验（`tools/robustness.py` → `out/<社区>/robustness.json`）

把关键假设各动一动重算：步速 1.10 / **1.25** / 1.35 m/s、阈值 810 / **900** / 990 s，
外加"保守端（1.10 + 810）"与"宽松端（1.35 + 990）"，共 7 个情景。**纯本地计算，不联网。**

| 社区 | 得分区间 | 跨度 | 等级 | 最短板要素 |
| --- | --- | --- | --- | --- |
| 曹杨新村 | 79.3–85.3 | 6.0 | 良好→优良 | 社区文化活动中心（各假设下均相同） |
| 长风新村 | 69.7–77.4 | 7.7 | 良好↔一般 | 同上 |
| 北新泾 | 77.7–82.9 | 5.2 | 稳定（良好） | 同上 |
| 程家桥 | 57.9–68.5 | 10.6 | 稳定（一般） | 社区食堂 / 老年助餐点 |
| 大场镇 | 64.4–74.7 | 10.3 | 一般↔良好 | 社区文化活动中心 |
| 合成数据集 | 65.7–75.3 | 9.6 | 一般↔良好 | 社区卫生服务站 |

**怎么读**：总分区间有 5–10 分的摆动，所以**不要拿总分当结论**；但"最短板要素"在所有假设下
基本不变 —— 补设施的方向是稳的。报告里两句话都写出来。

### 8.3 边际效益曲线（`tools/marginal.py` → `out/<社区>/marginal.json`）

对 k=1/2/3/4 各跑一遍选址优化，回答"为什么是 2 处"。曹杨新村（社区文化活动中心）：

| 建 k 处 | 覆盖率 | 累计新增覆盖 | 第 k 处边际增量 | 平均每处 |
| --- | --- | --- | --- | --- |
| k=1 | 91.5% | 19,033 户 | **+19,033** | 19,033 |
| k=2 | 99.5% | 22,653 户 | +3,620 | 11,327 |
| k=3 | 100.0% | 22,874 户 | +221 | 7,625 |
| k=4 | 100.0% | 22,874 户 | **+0** | 5,718 |

**口径提醒（踩过）**：累计新增必须用「基线不可达人口 − 建后不可达人口」的**并集口径**；
把各点位自报的 `newly_covered_households` 相加会重复计数同一组团（曹杨 k=3 时会算成 38,465 户，
比真实的 22,874 户多出 68%）。所以前端点位卡片上写的是**「单点新增覆盖」**，
并在优化后对比块里另给一行「合计新增覆盖（并集口径）」。

## 9. 已知局限（必须写进报告）

1. 未建模过街等待、坡度、天气、无障碍通行与电梯/天桥；
2. 设施容量按相对服务能力近似，未考虑实际规模（面积、床位、班数）；
3. 未区分开放时间、排队与预约；
4. 居住组团户数：合成数据是构造值；OSM 数据是"占地面积 × 层数 ÷ 91 m²（=35 m²/人 ÷ 2.6 人/户）"，
   并用 `landuse=residential` 范围把 `building=yes` 的住宅一并纳入，再按 120 m 网格聚合为组团；
   百度数据是缺省 600 户。三种来源在报告中都必须显式声明。实测曹杨新村真实数据集估算人口
   7.4 万（街道实际约 10 万量级），**偏低约 25%**，属估算口径误差，应视为下限；
5. 生活圈栅格精度 40 m，格点吸附到最近路网节点，离路网 >220 m 的格子不着色；
6. 要素清单与阈值需与国标/导则原文逐条核对后才能作为正式结论引用 ——
   现在每个要素都带 `standard_ref`（层级/出处/步行距离/面积口径/source_url），
   报告第 3.1 节列成表并逐条标「待核对原文」；核对完把 `verified` 改成 `true` 即可。
7. 总分对假设敏感（稳健性检验显示区间跨度 5–10 分），**引用时应给区间而不是单点**；
   报告第 7.1 节给出 7 个情景的重算结果与"最短板要素是否变化"。

## 12. JSAPI GL 底图模式的口径（与「体检底图」保持一致）

GL 模式（需 Web 端 AK）不是另一套逻辑，而是同一份数据的另一种画法：

| 图层 | GL 模式怎么画 | 为什么这么做 |
| --- | --- | --- |
| 覆盖色块 | 服务端把同一份栅格渲成**透明 PNG**，前端用 `GroundOverlay` 按分析范围贴上去（`/api/overlay.json`） | GL 里没法直接铺上千个多边形格子（会卡）；1 个透明叠加层就够，且与体检底图**同一份代码**，口径不会漂 |
| 15 分钟生活圈范围 | `circle_geojson` 并集多边形 | 与体检底图一致 |
| 居住组团 | 房子图标：**绿=达标 / 红=有短板 / 灰=路网未连通**，尺寸按户数 18–26 px | 颜色区分服务状况；灰色是「无法评估」，不能和「有短板」混为一谈 |
| 推荐点位 | 图钉 + 右上角编号**画在同一张位图里** | 早期用 `BMapGL.Label` 单独挂编号，拖动地图时标签与图钉各走各的；编号进图标后锚点完全一致 |
| 设施 | 默认**关闭**；勾选后需放大到 16 级以上才画 | GL 底图自带大量地名标注，100+ 个设施图标叠上去会糊成一片 |
| 一天动线 | `Polyline` 折线（白色描边 + 彩色线）+ 虚线离路段 + **序号+要素图标**的停靠点 + 出发点房子 + 播放小圆点，并自动把视野调到能看全 | GL 模式下 canvas 是隐藏的，动线必须单独画一遍，否则只有面板时刻表、地图上什么都没有 |
| 单组团等时圈（风圈） | 服务端渲的**透明 PNG**（分层色带 + 等时线 + 理想圆虚线，`/api/isochrone.json`）+ **圈上刻度用 GL `Label` 单独画** | 位图里的字一缩放就糊；刻度用标签画，任何缩放级别都清晰。叠加层与 canvas 模式共用同一份 `iso["grid"]` |
| 分析范围外的东西 | 一律不画 | 抓取范围外扩 1200 m 是为了**算得准**，不是为了画出来 |

点 GL 上的房子图标同样能生成「风圈 + 一天动线」，折线、序号停靠点、圈上刻度、缺口结论都与 canvas 模式一致。

## 13. 批次 4：住户画像、同心等时圈、界面双模式

### 13.1 住户画像（`config/personas.json`）—— 不接大模型现场判人

"一位老人一天会干什么"这件事，让人一眼看懂、又能被核对，靠的不是模型，是一张规则表：

| 画像 | 步速 | 出发 | 出行链 | 关键约束 |
| --- | --- | --- | --- | --- |
| 🧓 活力老人 | 0.85 m/s | 09:00 | 买菜 → 公园 → 卫生站 → 药店 → 社区食堂 → 文化中心 | 15 分钟只能走 **765 m**；单段超 12 分钟标黄 |
| 💼 双职工上班族 | 1.30 m/s | 07:20 | 送幼儿园 → 地铁（送到为止，不回家） | 幼儿园 **08:30 关门**是硬约束 |
| 👨‍👩‍👧 带娃家庭 | 1.00 m/s | 08:00 | 幼儿园 → 菜场 → 卫生站（儿保） → 公园 | 推婴儿车，单段超 10 分钟标黄 |
| 🎒 中小学生（放学后） | 1.30 m/s | 16:00 | 小学 → 文化中心 → 球场 → 便利店 | 时间由学校作息决定 |
| 🦯 行动不便者 | 0.60 m/s | 10:00 | 卫生站 → 药店 → 社区食堂（一趟办完） | 15 分钟只能走 **540 m**；单段超 5 分钟标黄 |

三条口径决定：

1. **步速乘进时间**：路网时间是按体检口径（1.25 m/s）预算好的，换步速**只做比例缩放**
   （`time = length / v`），不重建路网 —— 保证两种口径算的是同一张图。
   副作用是好的：同一条路，老人 15 分钟只能走 765 m，成人能走 1125 m，
   所以**不同画像的生活圈天然大小不同**，这正是"达标要和谁在走一起说"。
2. **设施不是全天可用**（`windows`）：菜市场 05:30–12:00、社区卫生服务站
   08:30–11:30 / 13:30–16:30（午间停诊）、社区食堂 10:30–13:30、幼儿园 07:15–08:30。
   到达时若已闭门 / 未开门，记为**服务时段冲突**并给出改法；早到 ≤15 分钟就地等，
   早到更久**不硬等**（否则一天会被拉长几小时），同样记成冲突。
3. **"特定住户"做不到，也不该假装做到**：我们没有（也不该有）居民个人数据。
   产品定位是「典型住户（画像驱动，可复现）」+「特定住户（画像 + 步速/出发时刻/停留时长
   三个可调参数）」。这是隐私友好的取舍，不是技术妥协。

大模型只适合出现在**两头**（把自然语言解析成画像参数、把结论翻译成人话），
**绝不进入中间**：不可复现、离线失效、演示有延迟风险，而可复现与离线可用正是本项目的卖点。

### 13.2 同心等时圈（风圈）—— 借风圈的视觉语言，不借它的圆

15 分钟生活圈在界面上有两种口径，含义不同、**不能叠着看**：

| 口径 | 圆心 | 回答的问题 |
| --- | --- | --- |
| 并集分带（`raster=isochrone`，图 2） | 全部居住组团 | 生活圈**画到哪儿**（从最近的组团出发多久能走到这里） |
| 单组团风圈（`focus`，图 3） | **某一个组团的家** | **我这一圈**的边界在哪、圈外被什么切掉了 |

风圈带三个可回答"为什么圈长这样"的量：

- **可达面积比** = 实际可达面积 ÷ 同半径理想圆面积。理想圆 = 以家为圆心、半径 = 步速 × 15 分钟，
  两者**在同一张栅格上取并集**才可比。曹杨某组团实测：15 分钟实际可达 1.14 km²、
  理想 1.89 km² → 可达面积比 **60%**，被吃掉 0.76 km²。
  低于 100% 的部分就是被河道、快速路、封闭小区、断头路吃掉的空间（图上画成灰底）。
- **16 个方向的可达半径**：找出被切断的方向。同一组团实测"南 190 m / 南南东 210 m"，
  而平均能走 532 m、最长 940 m —— 选址若落在这些方向，受益面会被限制。
- **每圈凑齐几项服务**：同心圈上最该有的刻度不是面积，是"走到这一圈为止能办成几件事"
  （实测 5 分钟 3 项 / 10 分钟 10 项 / 15 分钟 11 项）。

> **为什么不做成台风那样的同心圆**：台风圈是理想圆，这里画的是**真实路网上的等时圈**。
> 同样 15 分钟，隔着一条河、一条快速路，形状完全不同。画成几何圆等于主动放弃
> "用了真实路网"这个最大的技术差异点。

口径边界：圆心用组团质心（组团是 120 m 网格聚合出的分析单元，不是某一栋楼）；
面积统计范围限于**分析框内**（框外不计），所以贴边的组团可达面积比会被低估。

### 13.3 界面：体检 / 规划 双模式（做减法）

原来的问题是"报告该干的活跑到界面上来了"：7 张卡片一起滚，其中"要素体检"整张表、
"数据来源"整段都是**论证性**内容，不是**决策性**内容。原则一句话：

> **地图上做决策，报告里做论证。**

- 顶部一个 `① 智能体检 / ② 规划助手` 开关，切模式时整组卡片换一套：
  - **体检**：综合得分、六维、15 分钟圈（风圈）、问题清单；要素体检 12 项全表与
    数据来源收进折叠区（点一下展开，完整口径与标准依据在报告里）。
  - **规划**：处方（P1/P2 + 点位画像）、典型住户的一天（画像 + 时间轴 + 服务时段冲突 + 改法）。
- 演示节奏因此变成两个动作：**先体检（发现问题）→ 切规划（给出方案）**。

### 14.1 呈现方式：蒙版 + 高亮框 + 指向卡

早期版本只有一条顶部进度条 + 一段字幕，在整屏界面里几乎看不出"这一步在讲哪里"。
现在每一步：

1. **聚光**：四块蒙版把未讲到的区域压暗（`rgba(78,85,97,.62)`），只留目标元素的洞；
2. **高亮框**：橙色描边 + 外发光，套在目标外扩 8 px；需要观众动手的步骤再加脉冲动画；
3. **指向卡**：一条 SVG 折线 + 三角箭头从卡片指到高亮框；卡片里写
   **第 N 步 / 共 12 步 · 环节名**、正文、可选的 `👉 交互提示`、迷你进度条与读秒，
   以及「⏸ 暂停 / ↺ 重播本步」两个按钮；
4. **顶部控制条只留** 步数 + 总进度 + `⏸ 暂停 / 下一步 / ✕` —— 描述文字全部移入指向卡。

四个刻意的取舍：

| 决定 | 原因 |
| --- | --- |
| 蒙版用**一层 SVG mask 挖洞** | 四块矩形拼接的相邻边靠小数坐标对齐，浏览器各自取整会在接缝处漏出 1 px 亮线（用户实拍报过"蒙版有裂缝"）；单层 mask 从根上没有接缝。**而且矩形只能"加覆盖"、不能"减洞"** —— "同时高亮两处"（第 ⑧⑨⑩ 步：卡片 + 地图）做不了，mask 里加一个黑色 rect 就行 |
| 蒙版 `pointer-events: none` | 蒙住的是"还没讲到的区域"，但被高亮的那颗按钮必须仍然可点（第 ④⑦⑪ 步就是邀请观众自己点） |
| 指向线用 **SVG 折线 + 三角箭头**，不用 👉 | 彩色 emoji 在 Windows / macOS 上画法差别很大，压在深色蒙版上录进视频不专业；👉 只作为卡片里的点缀 |
| 指向卡选边 = **四条边外侧空间最大的一侧** | 目标可能在任一角落；固定位置会让折线绕远或指反。空间不足时退到次优侧并把卡片夹回视口 |

**同一屏高亮两处**（第 ⑧⑨⑩ 步）。这三步的"变化"发生在**地图上**（覆盖图层切换、动线播放、
换住户重算动线），只高亮右侧卡片的话，蒙版正好把要看的东西压暗了。所以这几步挖两个洞：
主目标（按钮 / 卡片）用**实线**高亮框 + 指向线 + 指向卡；地图用**虚线**高亮框 + 一个角标
（"动线正在地图上播放"）说明这里也在发生事情。角标会在四个角里挑一个不压住指向卡的角。

**节奏自动算**：`hold = clamp(3 s, 正文字数 × 0.15 s + 1.6 s + 框高加成 + 提示加成, 18 s)`，完整版再乘 1.45；
每步另有 **4 s 下限**。框高加成（`min(3.2 s, (框高 − 120 px) × 3.2 ms/px)`）是必须的：第 ⑦ 步的高亮框
是一整张处方卡（上千像素高），只按正文字数给 8 s 根本来不及看 —— 而且这一步 `run()` 里含
3–6 s 的选址重算，`want − spent` 会把阅读时间一起吃掉，所以第 ⑦ 步直接写死 `hold: 20000`。
实际停留（`tourcheck` 量到的）：12/12/13/14/16/10/**20**/9/17/13/12/10 秒。

### 14.4 工程上的决定（都是踩过坑才加的）

1. **卡片数字实时取自当前数据**，不写死 —— 换社区、换数据也不会说错话。
2. **单步失败只记一条"已跳过"，不中断**。GL 那一步额外三重兜底：没配 AK、`navigator.onLine === false`、
   9 秒内 `glState.map` 没就绪 —— 任一命中就留在离线静态底图上，**不会留一张白地图，也不会指向空气**。
   目标元素不存在时，指向卡改为居中、不画箭头，并把原因写进正文。
3. **定位高亮框之前先把目标滚到完整可见**（等 320 ms 让平滑滚动停下）——
   面板里被裁掉一半的卡片会让框落在视口外，指向线就指到空气上了。
4. **回退/跳转 = 从第 0 步快速重放**，而不是逐步撤销：每一步都改全局状态，撤销比重放容易出错。
5. **SVG 元素没有 `hidden` IDL 属性**：`el.hidden = false` 只是挂了个同名 JS 属性，
   HTML 上的 `hidden` 属性还在，CSS 的 `[hidden]{display:none}` 继续生效 ——
   表现为"高亮框正常、指向线死活不出现"。统一改走 `toggleAttribute('hidden', …)`。
6. **折线末段会退化**：卡片中心正对目标框中心时肘点与落点重合，
   箭头三角形三个点重叠、整个消失（这恰是最常见的一档）。方向要向 `A→T` 兜底。
7. **指向卡与高亮框留 56 px 而不是贴着放** —— 贴放时折线只有十几像素，
   看起来像卡片描边而不是指向线（实拍对比过）。
8. **长卡片滚动时会话框被甩到屏幕外**：目标被滚出可视区后，与视口求交会得到
   `bottom < top`，即负高度；CSS 里 `height:-12px` 是非法声明、**整条被丢弃** ——
   高亮框于是保留上一帧的尺寸，停在一个错误的 top 上。现在先判退化：退化时不画框与箭头、
   只留整幅蒙版；目标比屏幕高时把框高封顶（`H − 顶栏 − 150`）取可见部分居中，
   读起来才像"聚光"而不是"屏幕边框"。
9. **侧别必须稳定**：滚动触发重算时如果重新选边，卡片会在屏幕上跳来跳去。
   上一轮选的那一侧只要还放得下就继续用。
10. **蒙版的"裂缝"**：早期用四块矩形拼接，相邻边靠小数坐标对齐，浏览器各自取整 →
   接缝处漏出 1 px 亮线（用户实拍报告）。先改成"取整 + 相邻边叠 1 px"，
   后来要同时挖两个洞，干脆换成**一层 SVG mask**：接缝问题从根上消失，洞的数量也不再有上限。
11. **headless 浏览器要连子进程一起收**：Edge 会拉起一堆渲染进程，只 `terminate()` 启动进程
    的话它们继续活着占住调试端口 —— 下一次运行会连到上一次的僵尸实例上，而那个页面的标签
    早已被 Chrome 冻结，JS 完全停摆，`Runtime.evaluate` 于是永远不返回。
    表现是"脚本挂住不动、什么都不打印"（踩过一次，堆了 16 个 headless 实例）。
    现在：每次用**随机空闲端口**、URL 打上本次运行的标记、启动前清掉占端口的僵尸、
    收尾走 `taskkill /F /T /PID`，并且每一步都有 `--step-timeout` 兜底。
12. **演示里的等待用 `setTimeout`，不用 `requestAnimationFrame`**。这是同一类坑的第三次：
    无头浏览器里 rAF 会因为页面隐藏 / 标签被冻结 / `--virtual-time-budget` 而完全停摆，
    而"等一会儿再走下一步"全挂在它上面 —— 结果是页面看着还活着、演示却永远停在原地。
    定时器最坏被节流到 1 s 一次，但一定会来；进度条也不需要每帧刷新。
13. **`ResizeObserver` 会造成无限帧循环**：`observe()` 一定会先投递一次初始回调，
    所以"每次重摆都新建观察器"就等于"重摆 → 触发观察 → 再重摆"的自我激励循环，
    把帧预算吃光（同样是"页面活着但演示不动"）。现在观察器只建一次、换目标才
    unobserve/observe，并且**位置尺寸没变就不重摆**（`demoQueueReplace` 里的矩形键比较），
    地图画布干脆不观察。
14. **定位前要"滚到真的可见"，而不是等一个固定毫秒数**：平滑滚动缓入缓出、还会被下一次
    `scrollTo` 打断；卡片比面板高时居中还会把卡片顶部推到面板上方（目标直接落到视口外，
    高亮框量不到矩形就整个消失）。现在：高卡片顶对齐、量位置时用硬跳（`scrollTop =`）
    而不是平滑滚动、并最多三轮"量 → 不在视口里就再滚"收敛。
15. **重放时跳过重活**：`demoGoto` / 逐步自检会把前置步骤重放一遍，其中的选址优化（3–6 s）、
    动线计算、9 秒的动线播放动画都没必要重来。跳过之后 12 步逐步自检从 **384 s 降到 62 s**
    （每步 0.6–10 s），并且连跑三次结果一致。

## 15. 载体归并与社区去重（两个数据口径修复）

### 15.1 地铁载体：一座站只保留一条

**症状**：选址卡片上写"依托 行知路地铁站-1口"，地图上点位又紧挨着地铁图标，
读起来像"要把社区文化活动中心建在地铁口里面"；同时同一座站的多个出入口被算成
多个独立载体，候选环带在同一位置反复叠加、tier1 的 1.5 倍系数被重复放大。

**根因**：载体表和设施表口径不一致。

| | 数据来源 | 结果 |
| --- | --- | --- |
| 设施表（metro） | 原始 POI → 过滤出入口 + 250 m 按站合并 | 干净：`行知路`、`大场镇` |
| 载体表（tier1） | 原始 POI，只按 **120 m** 去重 | `行知路地铁站-1口`、`-3口`、`大场镇地铁站-地铁1通道口-客运交通枢纽`… |

出入口之间常超过 120 m，所以合并不掉。大场镇 tier1 的 5 条载体实际只对应 2 座站。

**修复**（`cluster_stations()`）：

1. 出入口/通道口 POI 按 **250 m** 归并到所属车站（与要素表 metro 同一口径）；
2. 归并后按**站名二次合并** —— 大型换乘站（如曹杨路站）的出入口能拉开 400 m 以上，
   只靠距离会切成一簇一簇、最后冒出两个同名载体；
3. 站体 POI 优先当代表，其次选带"地铁站/轨道"的名字（`行知路` → `行知路地铁站`）；
4. `is_valid_station_carrier()` 否掉归一后仍不像站名的：`无障碍电梯(上海动物园地铁站4号口)`、
   `行知路站地铁站安检区`、`追梦少年青年旅舍(场中路地铁站店)`。

结果：曹杨 11 → 4 座、大场镇 5 → 2 座、北新泾 2 → 1 座、程家桥 2 → 1 座。

**同时改了动词**：tier1/tier4 是「**邻近**」（借客流，设施在站点影响范围以外），
tier2/tier3 才是「**可合署**」（同一栋楼或同一院落）。原来一律写"依托"并不准确 ——
地铁出入口不是可以进驻的建筑。该字段（`CARRIER_META[*].relation`）会一直传到界面。

存量数据集用 `python tools/fix_carriers.py` 就地修（离线，不联网、不吃额度），
它会同时刷新 `meta.carrier_meta`（该字段在建数据集时写进文件，代码改了必须同步）。

### 15.2 重复添加同一社区：不再新建一份

**症状**：同一个街道用不同候选点搜索两次，社区下拉框里出现两个同名社区。

**根因**：`create_community` 每次都调 `slugify_community()` 生成新 id（`custom-xxx`、
`custom-xxx-2`）。而"大场镇"这类地名在百度 POI 里常同时匹配到镇上与地铁站，
两次搜索的中心点只差几百米，于是建了两份几乎重复的数据集。

**修复**：建库前先查已有社区，**同名且中心点相距 ≤ 500 m** 即直接复用并返回
`reused: true`，前端提示"该社区已存在（相距 N m），已直接切换"。
存量的 `custom-2af78a-2`（大场镇，与 `custom-2af78a` 相距 740 m）已移除。

## 16. 界面文案口径

对外可见的文字（图例、卡片、提示、报告、演示字幕）统一按以下原则：

1. **术语与本文档一致**：15 分钟可达覆盖率、要素达标率、供需均衡度、可达面积比、
   服务时段冲突、同心等时圈、出行链；不用省略主语的"覆盖率""达标率"。
2. **每个数字给出口径**：写"15 分钟可达覆盖率 49.4%"，不写"49.4% 人口可在 15 分钟内到达"
   （后者把"可达某一要素"说成了整句结论）。
3. **不用拟人化与口语**："这一站白跑"→"该次到访无效"；"被路网吃掉"→"受路网折减"；
   "红了很久的那片居民区"→"此前不可达的居住组团"；"一刻都耽误不起"→"构成刚性时间约束"。
4. **只陈述事实与可选处置**，不替使用方下结论：建议写作"可选处置：…"，不写"应该…"。
5. **动词要准确**：邻近 ≠ 合署 ≠ 依托（见 §15.1）。
6. **边界要写明**：凡涉及统计口径的图与卡片，必须说清统计范围。分析范围框的图例固定写作
   "分析范围（框外不参与体检）"，并在图注补一句"框外路网与设施仅在步行可达性计算中作为
   通路使用"—— 否则底图上框外可见的住宅区标注会被读成"漏画了色块"（见 §2.9）。

## 10. 一键复现

```bash
python tools/build_demo.py            # 生成 out/<社区>/report.md|html + diagnose.json
python -m unittest discover -s tests  # 指标回归测试（口径改动必须同步更新测试）
python tools/check_api.py             # 端到端 API 自检（含一天动线与点位画像）
python tools/robustness.py            # 稳健性检验（本地，7 个情景）
python tools/marginal.py              # 边际效益曲线（本地，k=1..4）
python tools/route_map.py             # 动线出图 + 风圈图 + 住户画像对比（本地，报告图 3/4 + 5.1/5.3）
python tools/compare.py               # 跨社区横向对比 → out/compare.html
python tools/stitch_network.py        # 断头路补连（本地，存量数据集）
python tools/name_clusters.py         # 居住组团实名（用百度小区 POI，走缓存）
python tools/scope_delta.py           # 分析范围口径核对：逐社区统计框外居住组团（--rebuild 对照重建前后）
python tools/tour_shots.py --check    # 一键演示逐步自检（CDP 驱动无头 Edge，实跑 12 步）
python tools/tour_shots.py 2 3 7 11   # 逐步取景截图 → out/tour/stepNN.png
python tools/basemap_align_probe.py   # 底图比例尺与残余平移的定量核验
```

**两个跑批注意事项**（都踩过）：

1. **`demoall` 里 `route_map.py` 必须排在 `build_demo.py` 之前**。`report.md/html` 会内嵌风圈
   （`focus_iso.json`）与动线的结论，而这两份数据由 `route_map.py` 产出 —— 顺序反了，报告
   里的风圈文字会滞后一轮（图是新的、话是旧的）。`tasks.ps1` 已按正确顺序固定。
2. **Windows 管道的默认编码是 GBK**，而口径文本里含 `km²`（U+00B2），GBK 编码不了。
   `build_demo.py` / `check_api.py` / `make_package.py` / `verify_package.py` / `scope_delta.py`
   都在开头把 stdout 重设为 UTF-8 —— 否则脚本会在**最后一行 print 时**才炸并以非零码结束，
   看起来像"构建失败/自检失败"，其实活已经干完了。
