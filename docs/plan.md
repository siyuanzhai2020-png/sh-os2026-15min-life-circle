>
> 计划与最终实现的主要差异（均为立项后的刻意收窄，理由见下表）：
>
> | 计划内容 | 实际实现 | 原因 |
> | --- | --- | --- |
> | 前端 Vue3 + Vite + Tailwind + ECharts | **零依赖** canvas / SVG / 原生 JS | 收件人不需要 npm install 就能打开；离线可用；规避演示环境依赖安装失败的缺陷 |
> | 报告 Jinja2 模板 + Playwright 截图 | 自研 Markdown/HTML 渲染 + PIL 出图 | 少两个重依赖；出报告与 PDF 都不需要浏览器 |
> | igraph 做大规模最短路 | 纯 Python 手写 Dijkstra + 邻接表 | 单社区 7000+ 节点足够快，且省掉一个 C 扩展依赖 |

> | LLM 将指标转写为文字说明 | 未接入（画像与建议均为规则生成） | 评审更看重可复现与可追溯，规则化措辞更便于核对 |
>

## 1. 立项目标与赛题

> 赛题：2026 上海开源软件应用创新大赛 ·【开源 AI 工具赛道】百度地图赛题
> 目标：4 周内交付「可跑、可演示、可自证指标、可复现」的开源项目

## 2. 赛题评审关注点

赛题字面要求为「助手」，评审差异主要体现在三方面：

1. **地图开放能力的应用深度** —— 仅用地点检索与打点标注为及格线；用 JSAPI GL 自定义图层、路径规划/等时圈与分级着色为良好；把「可达性」实现为可解释的算法结果为优秀。
2. **体检指标体系的口径出处** —— 达标口径不得自行定义，需对标：
   - GB 50180-2018《城市居住区规划设计标准》的居住区分级（十五分钟生活圈居住区 = 步行距离 800~1000 m，人口 5~10 万；十分钟 500 m；五分钟 300 m）
   - 上海《15 分钟社区生活圈行动》与社区生活圈规划导则的"五宜"与分要素配置要求
   - 文档需引用**原文条目**（以官网/国标原文核对要素清单与距离口径），不以印象列设施清单；评分依据为口径来源的可追溯性。
3. **规划建议能力** —— 由"诊断"延伸到"处方"：给定预算新增 K 个设施，推荐点位并量化覆盖增益。该步骤在评审中易被忽略，也是较易获得加分的环节。

项目定位：**社区生活圈体检引擎 + 选址建议器**，不做通用聊天地图；LLM 仅负责把指标结果转写为文字说明。

## 4. 指标体系 v1（立项期先冻结口径）

| 指标 | 定义 | 数据来源 | 说明 |
|---|---|---|---|
| 15 分钟可达覆盖率 | 居住点位中，步行路网距离 ≤ 1000 m（或等时圈 ≤ 15 min）可达**某类设施**的比例 | 步行路网 + POI | 主口径建议用**路网距离**，等时圈做辅证 |
| 要素达标率 | 对要素清单（菜场/生鲜、社区卫生服务站、社区食堂或助餐点、药店、幼托、小学、文化活动中心、健身步道或球场、公园绿地、公交/地铁站点…）逐项判定 | POI + 国标/导则清单 | 清单以官方原文为准，每项标注出处 |
| 供需缺口指数 | 设施服务能力（数量/面积/开放时间）÷ 覆盖人口 | POI + 人口栅格或小区户数 | 无人口数据时用 WorldPop 100 m 栅格近似，并声明假设 |
| 单一依赖度 | 只被 1 个设施覆盖的人口占比 | 可达性矩阵 | 抗风险能力，很少人做，容易出彩 |
| 公平性 | 街道内各小区达标率的极差 / 标准差 / Gini | 指标聚合 | 体现"生活圈"的公平内涵 |
| 绿色可达性 | 步行、骑行可达的设施占比（相对机动车依赖） | 多模式路径 | 与"15 分钟"的低碳初衷呼应 |

**关键决策：可达性由项目自算，不依赖批量算路配额。** 做法为 OSM 步行路网 + 图最短路自建等时圈，百度地图负责 POI 检索、地理编码与抽样校验。理由：批量算路与等时圈高级接口的配额与审批不可控，接口受限将导致整体项目中断；自算同时使算法成为可写入文档的技术贡献。

## 5. 技术选型

| 层 | 选型 | 选型理由 |
|---|---|---|
| 数据/算法 | Python 3.11、GeoPandas + Shapely、OSMnx、igraph、H3、pandas、NetworkX（小图调试） | 地理算法生态最全；igraph 做大规模单源最短路比 NetworkX 快一个量级 |
| 服务 | FastAPI + SQLite（或 PostGIS）+ Redis + APScheduler | 轻量可复现；预计算任务与在线查询分离 |
| 前端 | Vue3 + Vite + BMapGL（百度地图 JSAPI GL）+ ECharts + Tailwind | JSAPI GL 支持自定义图层与 3D，等时圈/热力/分级着色都能画 |
| 报告 | Jinja2 模板 + Playwright 截图 → Markdown/PDF | 报告可复现、可进 CI |
| LLM（可选） | 任意 OpenAI 兼容 API | 只做文字组织与建议表达；**所有数字必须来自指标引擎** |
| 部署 | Docker Compose | 评审可一键运行，其重要性高于增加附加功能 |

## 7. 四周排期

### W1 — 数据链路与口径（周末验收：能对 1 个社区画出 15 分钟等时圈）
- 申请百度地图开放平台 AK（实名），确认地点检索/地理编码配额；如可申请高级权限（等时圈、批量算路）一并提交
- 采集 2~3 个试点社区的 POI：分类检索 + 分页 + 落地缓存（原始响应 + 哈希 + 采集时间）
- 下载/裁剪 OSM 步行路网，做拓扑连通性修复（断头路、跨河桥）
- 跑通 POC：单点 15 分钟等时圈（igraph 单源最短路 → 到达时间栅格 → 等值线）
- **冻结指标表 v1 到 `docs/metrics.md`**，每项标注国标/导则出处

### W2 — 指标引擎（周末验收：命令行跑出社区体检 JSON）
- 居住点位/小区面数据准备（可用建筑轮廓或小区 POI + 户数假设）
- 可达矩阵与等时圈预计算，结果落库（H3 网格聚合，控制规模）
- 实现 6 项指标 + 分要素达标判定，输出结构化 `diagnose.json`
- 用百度路径规划抽样校验 30~50 条，量化自算路网与官方路径的偏差（写进误差分析）
- 单元测试覆盖指标计算（固定小样例，防止口径漂移）

### W3 — 可视化与报告（周末验收：产出可展示的报告 + 网页 Demo）
- 前端：社区选择、等时圈图层、设施分级着色、缺口热力、指标雷达图
- 报告生成：模板 + 图表 + 地图截图，一键导出 Markdown/PDF
- LLM 段落接入（可选）：基于 `diagnose.json` 生成诊断叙述，禁止自由发挥数字
- Docker Compose 打包，写 README（含 3 分钟跑通指引）

### W4 — 选址建议 + 打磨提交（周末验收：完整演示视频 + 提交材料）
- 选址优化：设施类型 → 候选点位（POI 空白网格 / 可用地块）→ 贪心最大覆盖（MCLP 思路）→ 局部搜索提升 → 输出覆盖增益与前后对比
- 复制到第 2、3 个社区，验证泛化（一个成熟老社区 + 一个新城/郊区）
- 补文档：架构、算法、口径、误差、复现步骤、依赖与许可证
- 录 3 分钟演示视频；检查开源合规（许可证、数据使用声明、`NOTICE`）
- 提交前自测清单逐条过一遍

**性价比最高的差异点**：把"指标引擎"拆成独立可复用的 Python 包（`lifecycle_metrics`），可直接被外部项目引用；开源赛事中"可被复用"的得分权重通常高于"功能多"。

## 9. 风险与预案

| 风险 | 概率 | 影响 | 预案 |
|---|---|---|---|
| AK 审批/配额受限 | 中 | 高 | 第一天就申请；全部外部调用本地缓存并版本化；核心链路（可达性）不依赖配额 |
| OSM 步行数据质量差（断头、缺天桥） | 中 | 中 | 拓扑修复 + 与百度路径抽样比对，公开偏差数据作为诚实性加分项 |
| 大规模路网计算太慢 | 高 | 中 | 只对居住点位算（不做全栅格）；igraph + 预计算落库；H3 降采样 |
| 人口数据缺失 | 高 | 中 | 用 WorldPop 栅格或户数假设，并在报告中显式声明假设与敏感性 |
| 被评"就是个地图套壳" | 中 | 高 | 演示重点放在算法与建议闭环，视频前 30 秒直接给"某社区缺 3 类设施 + 推荐点位"的结论 |
| 数据合规 | 低 | 高 | 遵守开放平台条款；仓库只存聚合结果与缓存元数据；报告注明来源与用途 |
| 4 周时间不够 | 中 | 高 | W3 结束即冻结功能，W4 只做打磨；加分项（选址优化）可裁剪为"单类型设施" |
